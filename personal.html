AI Job Application Pipeline
Goal & Motivation
Tools like LinkedIn Premium charge money to do what should be straightforward: find relevant internships, filter out the noise, and apply efficiently. I wanted to build a free version that did the same thing. The target was hardware, embedded systems, and electrical engineering internships across California. I also wanted to see how much of the process I could actually automate using AI, since people sell these pipelines as products.
How I Built It
Built in Python with several components working together. python-jobspy handles scraping from Indeed and LinkedIn using broad keyword searches so the scorer handles filtering rather than the scraper. The Claude API (claude-sonnet-4-6) scores each listing 1-10 with an apply/review/skip recommendation based on skill overlap, seniority level, and industry fit. gspread 6.x logs every scored result to a Google Sheet with deduplication by URL so nothing gets double-logged. Playwright handles browser-based auto-fill for applications. A searches.yaml config file manages all keyword and location combinations so nothing is hardcoded. The cover letter generator uses the Claude API with writing samples to match tone. CLI is built with typer and rich. I intentionally used AI for scoring since manually reading hundreds of job descriptions to filter them is slow and inconsistent.
Results & Lessons Learned
The pipeline scrapes, deduplicates, scores, and logs listings end to end. Cover letter generation produces usable first drafts. Main debugging issues were gspread 6.x auth API changes and jobspy parameter changes between versions. Both are good examples of why external dependencies need defensive handling. The automation handles the volume side well. Deciding which specific jobs are actually worth applying to still takes a manual look.

Water Distribution Monitor
What I Built
During my summer internship at Raytheon Technologies in 2022, I worked on a water flow monitoring concept. The device is an in-line motorized valve that mounts on a water pipe, reads flow rate continuously, and closes automatically when the reading exceeds a set threshold. I designed the full assembly in Fusion 360 and wrote prototype logic in C to simulate the automatic shut-off behavior.
CAD Design
The Fusion 360 assembly has two main parts: an ABS housing block that clamps around a copper pipe, and a rotary valve mechanism on top. The cross-section view shows the concentric sensor ring structure inside the housing. The front panel has a water level reading display. Engineering drawings use standard multiview layout with front, top, and side projections. The material spec is ABS plastic for the housing and copper for the pipe, at 1:2 scale.
Control Logic
The prototype code reads flow rate in L/min and compares it against a configurable threshold each second. When the reading exceeds the limit, it triggers a close routine that simulates a servo motor rotating 90 degrees to shut the butterfly valve. Once closed, a lock flag prevents the system from reopening without a manual reset. In a real deployment, the simulated readings would come from a physical flow sensor over analog or serial input.
Prototype Code
// Benjamin's Smart Water Monitor - Prototype Logic // I wrote this to simulate the automatic shut-off feature for my design portfolio. // It mocks up sensor data to show how my physical valve will react to a leak. const int maxFlowThreshold = 20; // I set the max allowable flow to 20 L/min for testing int simulatedFlow = 5; // Starting at a normal 5 L/min bool systemLocked = false; // Keeps the valve closed once triggered void setup() { Serial.begin(9600); // Boot up message for my serial monitor demo Serial.println("--- Booting Benjamin's Water Monitor V1 ---"); Serial.println("Checking sensor baseline..."); Serial.println("Valve is currently: OPEN (0 degrees)"); Serial.println("-------------------------------------------\n"); delay(1500); // Give the serial monitor a second to catch up } void loop() { // If the valve is already closed, stop running the loop if (systemLocked) { return; } // Simulating a leak by increasing the flow rate randomly over time simulatedFlow += random(2, 6); Serial.print("Current Reading: "); Serial.print(simulatedFlow); Serial.println(" L/min"); // Main logic check: if flow passes the limit I set, close the valve! if (simulatedFlow >= maxFlowThreshold) { Serial.println("\n[!] WARNING: Flow rate exceeded threshold!"); Serial.println("[!] Potential leak detected."); closeValve(); } delay(1000); // Reading the sensor once per second } void closeValve() { Serial.println("Activating my servo motor..."); // In the real prototype, this is where I'll send PWM signals to rotate the butterfly valve 90 deg delay(800); // Simulating the physical time it takes the motor to turn Serial.println("Motor reached 90 degrees. Valve is now CLOSED."); Serial.println("Updating LCD screen to RED warning state."); Serial.println("System locked safely. Manual reset required.\n"); systemLocked = true; // Flag it so it doesn't keep trying to close }

Air Quality Monitor Deployment — Azusa
Goal & Motivation
Azusa didn't have detailed local air quality data. As a Research Intern with UCI Environmental Injustice Research, I deployed monitors across multiple sites to collect CO2 and pollutant readings and figure out which areas were most affected.
How I Fulfilled the Requirements
Deployed air quality monitors across multiple businesses and sites in Azusa to collect CO2 and pollutant level data over time. Compared readings across locations and cross-referenced results against city topography to understand how geographic features influenced pollutant concentration and dispersion.
Results & Lessons Learned
Analysis pointed to which zones had higher pollutant levels and why. Compiled findings into a presentation for faculty and stakeholders. Monitor placement mattered a lot — putting one in the wrong spot relative to airflow gave misleading readings even when the hardware was working fine.
